# Can Odin drive native AppKit well enough to rewrite Sendpoint?

**Research date:** 2026-09-30 · **Ticket:** [#47](https://github.com/saiashirwad/sendpoint/issues/47) · **Map:** [#35](https://github.com/saiashirwad/sendpoint/issues/35)

## Answer

**Yes: Odin can implement Sendpoint's native AppKit UI and macOS integration without Swift. This is a conditional engineering go, not evidence that the whole rewrite is low-risk.** A working, committed Odin-only spike runs an NSApplication delegate, menu-bar status item, non-activating NSPanel subclass, custom NSView with Core Graphics/Core Text drawing, editable native text controls, vibrancy, stack/anchor layout, animation, and appearance callbacks. The fundamental question is no longer “can Odin call AppKit?” It can. The work is maintaining correct bindings, explicit lifetime/thread ownership, native UI behavior, and replacing the existing Swift-based speech integration.

**Scope supersedes the original web-shell question:** the requested destination is a ground-up Odin rewrite with native AppKit UI and app logic. No web UI, webview, Electron/Tauri, or script-message bridge is proposed or retained in the spike. Swift is avoidable for AppKit itself; keeping the current FluidAudio implementation unchanged would preserve a Swift dependency, so that part needs a separate replacement/port decision rather than being disguised as “thin glue.” [S1–S5, S15]

## What actually ran

Sources and reproduction instructions: [`odin-appkit/`](odin-appkit/README.md). No app files were changed; no Sendpoint build/install/release script was run.

- Host: arm64, macOS **27.0 (26A428)**, installed Odin **dev-2026-09:a2fb372b7** ([full compiler revision](https://github.com/odin-lang/Odin/tree/a2fb372b76e81ef31fbbc8a2cf2b4fdf5ac6c924)). Also inspected upstream source at `9404e421313e363070bc6b6541ecc39946e4f1ed`; do not confuse source inspection with running that newer compiler.
- Final native UI: built and ran twice with Core Graphics/Core Text drawing; automatic stop and explicit teardown completed. It reported **panel visible=true, application active=false**; all six launch/dispatch/block/draw/edit/animation assertions passed; three effective-appearance callbacks arrived. The panel has the non-activating style from construction and implements key/main-window policy.
- Separate compiler-generated subclass: `@(objc_implement=true, objc_superclass=NS.Object)` returned **47** through Objective-C dispatch.
- System-boundary probe: AVAudioEngine allocation succeeded (not running); AVCaptureDevice audio authorization status **2 / denied**; SMAppService main service existed but status **3 / not found** for the unbundled executable; AX object creation/release succeeded with **AX trust=false**; CoreAudio default-input query returned **OSStatus=0**, with a device.
- Third-party generated binding probe: `darwodin` created an NSTextField through its typed AppKit/Foundation packages. Its AppKit package also passed `odin check ... -no-entry-point`.

**Evidence limits matter:** these are short executable proofs, not screenshots or UX certification. Text-edit notification was programmatically induced, not typed; keyboard focus/IME/undo and foreground-app preservation during real editing remain untested. `hasAmbiguousLayout=false` was checked on the root only. Appearance was changed on this view, not in system settings. No microphone recording, permission prompt, global hotkey registration, selected-text retrieval, login registration, signing/notarization, Intel execution, leak test, latency measurement, or idle CPU/RAM benchmark was performed. [S1]

## 1. Interop maturity: useful compiler support, incomplete batteries

### Three mechanisms, not one

1. **`intrinsics.objc_send`** compiles a typed message send from the return type, receiver, selector, and arguments. The compiler backend selects the appropriate message-send ABI variants, including structure/floating-point cases; this is preferable to hand-casting one generic `objc_msgSend` signature everywhere. But the caller still supplies the correct Apple signature: a selector string is not a checked SDK declaration. Our spike explicitly uses pointer-sized `int`/`uint`, `f64` CGFloat on this 64-bit target, `NS.BOOL`, and NSRect. The intrinsic requires a compile-time selector string; the layout helper therefore uses compile-time string parameters. [S2, S1]
2. **`@(objc_class)` / `@(objc_type)` / `objc_selector` / `objc_name`** attach Objective-C class/method metadata to Odin declarations. They support typed imported methods and convenient member-like calls; the generated-binding probe demonstrates `UI.TextField.textFieldWithString(...)` across packages. `objc_class` alone does **not** mean “register my new subclass.” [S2, S4]
3. **Implementations** can be made either with `objc_allocateClassPair` + `class_addMethod` + `class_addProtocol` + `objc_registerClassPair`, or with the newer compiler attributes `objc_implement`, `objc_superclass`, `objc_ivar`, and `objc_context_provider`. The UI spike deliberately proves the explicit runtime path; the tiny attribute probe proves the compiler path independently. Darwodin's Metal sample uses compiler-defined app delegates/views and context-bearing instance variables. [S3, S4]

A concrete footgun: embedding `NS.Object` in an Odin struct did not itself establish runtime Objective-C inheritance in the attribute probe. Omitting `objc_superclass=NS.Object` compiled but trapped when messaging the resulting object; adding the explicit superclass fixed it. This was a probe-author error, not proof of an unfixed compiler bug. Likewise, dynamic class objects need an appropriate receiver cast for `objc_send`; the intrinsic rejected a raw `Class` pointer. [S1]

### What is actually in core/vendor

`core:sys/darwin/Foundation` now includes many **AppKit** objects despite its name: NSApplication, NSWindow, NSPanel, menus, events, cursor, color, image, open/save panels, etc., plus runtime/delegate helpers and blocks. NSPanel's own file is only a type declaration inheriting Window. It is not a complete native-widget toolkit: the inspected directory has no full NSView/NSTextView/NSTextField/NSStackView binding set. `vendor:darwin/Foundation` is a **migration stub that panics**, telling you to import `core:sys/darwin/Foundation`. Other vendor Darwin packages cover Metal, MetalKit, QuartzCore, and CoreVideo, not a complete set of Sendpoint APIs. CoreGraphics in core has a small display/cursor/key-state subset, not the full drawing/event-tap API. [S3]

**Important counterweight: do not conclude that all missing declarations must be handwritten.** [harold-b/darwodin](https://github.com/harold-b/darwodin) has extensive generated AppKit, Foundation, CoreGraphics, CoreText, AudioToolbox, AVFoundation, QuartzCore and other bindings. At examined commit `08a4e282...`, its README says generated against macOS/iOS **26.2**, acknowledges missing frameworks and imperfect generic/enum treatment, and its source includes native controls, delegates, layout anchors, animation and view subclasses. The package and small executable checks passed on our compiler. This is a strong starting point, **not a validation of every API**: inspected framework folders did not include ServiceManagement or CoreML, and SDK 27's audio-tap addition requires newer declarations. Pin the compiler, SDK and binding commit together. [S4]

**Recommendation:** use a narrow, reviewed platform package, taking typed declarations from a pinned generated source where they work. Do not scatter raw selector strings, numeric enum constants, or `Obj` casts throughout app views as the exploratory spike does. Keep runtime subclass registration as a proven fallback while testing compiler-defined classes against the actual app patterns.

### What “no Swift” means for the current dependencies

Sendpoint currently imports **FluidAudio**, uses `StreamingUnifiedAsrManager` through async/actor-owned workflows, and imports **Sparkle**. Odin's Objective-C interop does not automatically make arbitrary Swift actors, generics and async methods callable. Retaining FluidAudio unchanged therefore means a Swift implementation behind a deliberate C/Objective-C boundary; it does not meet a strictly Swift-free dependency goal. A Swift-free rewrite must instead select a compatible C/C++ inference runtime or port the required Core ML/transcription pipeline and model handling. That decision must prove Parakeet Unified behavior, streaming latency, memory and acceleration independently. **This report did not validate such a replacement and does not authorize silently swapping speech models.** [S15]

Sparkle has public Objective-C-facing APIs, so it is not intrinsically tied to a Swift host, but packaging/signing/update delegate integration remains work. Prefer public APIs rather than copying the core Foundation helper's explicitly non-public `setAppleMenu:` convenience. [S3, S16]

## 4. Ownership, callbacks and ABI are the real rough edges

- **No ARC for your Odin code.** Balance alloc/new/copy/retain with release; CF Create/Copy results with CFRelease. Distinguish autoreleased returns from owned values. Objective-C ownership of a view subtree is not ownership of arbitrary Odin pointers stored in callbacks. Keep delegates/targets and block contexts alive until callbacks cannot run. The spike explicitly retains its status item/delegate, detaches delegates/targets, invalidates its exit timer and releases views before draining the outer pool. A short successful run is not a leak proof. [S1, S3, S10]
- **Autorelease pools are per-thread.** NSApplication handles normal event-loop pools; add a startup pool and scoped pools for background batches that make Cocoa calls. A single never-drained worker pool still lets temporary objects grow without bound. [S10]
- **Blocks are objects with an ABI, not C function pointers.** Core's `Block_createLocal` actually copies a temporary stack block to heap; it does not return a dangling stack block. Its `WithParam` variant is one explicit argument and void return. It stores raw user-data/procedure pointers and has no general captured-object ownership machinery. The “global” helper allocates Odin memory but marks the block global, so ordinary block release is not a normal ownership solution for that allocation. Audit these exact helpers before extending them; the Clang ABI defines invoke/copy/dispose/signature fields. Our timer and animation blocks worked after releasing our creation references; that does not establish arbitrary block signatures. [S9]
- **Foreign callbacks use `proc "c"`, not ordinary Odin's implicit-context calling convention.** The spike establishes an Odin context on entry. Production code should use the correct durable allocator/context and avoid sharing a temporary allocator across asynchronous work. Compiler-defined classes can use `objc_context_provider` to recover their context; darwodin demonstrates this. [S2–S4]
- **Main-thread ownership is explicit.** Keep AppKit mutation and UI-owned state on main; dispatch completed results back using `dispatch_async_f` (proven) or typed blocks. C-style dispatch is convenient because it avoids blocks entirely for this handoff. Queued raw userdata must survive until execution; attach operation/generation IDs so cancelled or superseded requests cannot update current state. UI animation completions need the same stale-result discipline as microphone/AX work. [S1, S11]
- **Superclass calls need care.** The runtime-subclass appearance override calls superclass dispatch using `objc_msgSendSuper2`, whose super structure contains the current class (lookup starts above it). Redeclaring this foreign symbol with a different signature conflicted with Odin's runtime declaration; matching the runtime declaration and using a typed function pointer for the actual call worked. Compiler/generated support also exists—an old open request alone is not proof it is impossible today. Test each signature, especially struct returns and Intel builds. [S1–S4]
- **Availability/errors/exceptions are yours.** Raw selectors are not Swift's availability checking or `throws` conversion. Gate OS-only APIs, handle NSError**/OSStatus/nil, and avoid invalid arguments that raise NSException. There is no demonstrated general Objective-C exception-recovery boundary in these probes; a very small C/Objective-C shim remains a reasonable escape hatch without introducing Swift. [S6–S8]

### Observed toolchain pitfalls

**Deployment target:** the default build on this machine emitted Mach-O `minos 28.0` with SDK `27.0` despite executing locally on 27.0. This matches the class of problem reported in Odin [#7066](https://github.com/odin-lang/Odin/issues/7066). **Explicit `-minimum-os-version:13.0` fixed the inspected load command to 13.0**, and the same native spike ran successfully. Set a deliberate minimum, inspect the final binary, and test on that OS; a corrected load command does not prove compatibility. [S1, S12]

Odin [#7131](https://github.com/odin-lang/Odin/issues/7131) reports an LLVM assertion for imported Objective-C class methods on a July compiler. It was open when inspected; our narrower generated AppKit class-method call passed on September Odin. Treat it as a regression test candidate, not as a reproduced current blocker. Do not use `-bedrock`: the compiler's help explicitly lists Objective-C support among the features it disables. [S12]

## 5. Real projects: what the evidence does and does not show

- **`hw_activity_monitor`**, examined at `d5783c65...`, has published downloadable macOS releases (v1.3.0, 2026-09-20), a status item, borderless non-activating panel, explicit Objective-C runtime glue and main-queue C dispatch. Its own README says the panel's content is Clay/Metal/CoreText-rendered rather than a native AppKit control hierarchy. This is unusually close evidence for Odin as a native macOS host, but not proof of a full native text-editing application or a large established user base. Inspected source; did not install it. [S13]
- **IceShot**, examined at `8ac64519...`, has downloadable macOS builds (v2026.08.13 and earlier). Crucial qualification: its menu-bar daemon's `main.m`, `tray.m`, `hotkey.m`, `config.m` are **Objective-C**; its worker is Odin/raylib with additional native Objective-C code. It proves shipping an Odin-containing Mac utility, **not** a pure-Odin native-AppKit app. [S14]
- **Darwodin** is a serious platform-binding project with a native AppKit/Metal delegate/view sample, not a shipped Sendpoint-like product. Its generated AppKit probe ran here. It reduces the binding-writing burden substantially but does not remove lifetime/ABI review or current-SDK validation. [S4]

Searches included GitHub repository queries for macOS/Odin and code searches for NSView/NSTextView. I did **not** establish a mature, broadly deployed, pure-Odin application using the full native AppKit text/control stack. That is an evidence gap, not a claim that none exists. Small recent released utilities and a working local prototype are meaningful evidence, but should not be inflated into Cocoa ecosystem maturity.

## 6. Recommended path for the chosen Odin rewrite

The user has chosen Odin/native AppKit; the recommendation is **how to make that choice safe**, not to restore the discarded web/Swift architecture.

1. **First establish a small platform contract.** Pin Odin + SDK + darwodin revision; test imported methods, compiler subclasses/runtime fallback, superclass calls, blocks and deployment metadata in CI. Keep typed binding code separate from pure app logic. Permit a tiny C/Objective-C ABI helper only where it genuinely simplifies safe ownership or exceptions; no Swift is required by the UI proof.
2. **Build one actual Sendpoint surface, using native text controls.** Validate non-activating focus with another foreground app, multiline/IME/undo, menu commands, VoiceOver, keyboard navigation, live resizing, appearance changes, Reduce Transparency/Motion, Spaces/fullscreen, multiple displays and Retina scale changes. Use drawRect/CoreText for custom non-editor visuals, native Auto Layout/NSStackView for normal controls, and manual layout only behind clear subtree ownership.
3. **Port the native input/audio seams before the entire UI.** Real hold → AX read → audio capture → release/cancel with hotkey conflicts, denied/revoked permissions, device removal, stale callbacks and repeat teardown. Measure end-to-end latency and hidden/idle footprint. Current proofs stop before these integration gates.
4. **Resolve Swift-free Parakeet Unified explicitly.** A native AppKit success does not solve the FluidAudio replacement. Require a streaming/inference spike on the desired runtime before declaring the rewrite dependency-complete.
5. **Carry lifecycle discipline into Odin.** Closed workflow enums/tagged unions, one event transition function, one effect/lifecycle owner, retained cancellable handles, generation checks and idempotent teardown. Plain pointers and callbacks make this more important, not less. Test pure domain transitions independently from AppKit and run native integration/UI tests with a stable signed app identity.

**Bottom line:** no fundamental AppKit interop blocker was found, and the native UI is demonstrated rather than hypothetical. Budget this as an Odin app **plus a maintained macOS binding/lifecycle layer**, not as “Swift syntax translated to Odin.” The highest unresolved risks are speech-runtime replacement, long-lived ownership/cancellation, real text/focus behavior, deployment and permission integration—not creating windows or drawing native UI.
